## 1. 목적

우리가 발급했거나 사용 중인 API Key가 **외부에 노출되어 있는지** 자동으로 점검한다.
우리는 해당 키의 **평문을 보관하지 않고**, 다음 정보만 가지고 있다.

| 항목 | 설명 | 예시 |
|------|------|------|
| `prefix` | 키 문자열의 앞부분 (약 7자) | `sk_live` |
| `postfix` | 키 문자열의 **실제 끝부분** (약 7자) | `a1b2c3d` |
| `sha256` | 키 **평문 전체**의 SHA-256 해시 (hex 64자, 솔트 없음) | `9f86d08...` |
| `length` | (선택) 키 전체 길이 — 사용자가 커스텀 | `48` |
| `charset` | (선택) 중간부 문자셋 — 사용자가 커스텀 | `base62` |

점검은 2단계로 나뉜다.

- **1단계 — GitHub**: 공개 저장소에 키가 커밋되어 있는지 (GitHub Code Search API)
- **2단계 — 외부 웹**: 블로그·포럼·문서 등에 키가 게시되어 있는지 (웹 검색 API)

노출이 확인되면 **노출 위치 링크**와 **삭제 권고문**을 리포트로 반환한다.

## 2. 확정된 설계 결정

| # | 항목 | 결정 |
|---|------|------|
| 1 | 해시 대조 | SHA-256, 솔트 없음. 후보 문자열을 그대로 해싱해 대조 |
| 2 | **외부 검색 쿼리** | **Prefix + Postfix 결합 쿼리(`"{prefix}" "{postfix}"`) 필수 적용**. 단순 prefix 검색 시 발생하는 전 세계 수십만 건의 노이즈를 99.99% 압축해 내 키를 핀포인트로 특정 |
| 3 | **전수 탐색 (Deep Scan)** | 단일 페이지(50~100건) 제한 탈피. **페이지네이션(`page=1..N`)을 순회하여 상한(최대 1,000건)까지 전수 조사** |
| 4 | GitHub 범위 | 공개 저장소 대상, GitHub Code Search API 사용. 필요 시 org/repo/extension 등 검색 한정자(qualifier) 확장 지원 |
| 5 | 웹 검색 | 공급자 인터페이스 추상화. **기본 구현 = Brave Search API**, Google CSE / SerpAPI 교체 가능 |
| 6 | API 동작 | **비동기 잡 + 폴링**: `POST /scans` → `job_id`, `GET /scans/{job_id}` 로 결과 조회 |
| 7 | 토큰 구조 | prefix ≈ 7자, postfix ≈ 7자(실제 끝부분), 하나의 연속된 토큰. length·charset 은 요청에서 커스텀 |
| 8 | 키 종류 | **자체 포맷 + 서드파티 모두 지원** — 탐지 규칙을 플러그인형으로 구성 |
| 9 | 결과 전달 | **v1은 JSON 리포트만**. Slack·이메일 알림은 확장 지점만 설계 |
| 10 | 상태 저장 | **무상태**. 잡 상태는 메모리에만 유지, 재시작 시 소실 허용 |
| 11 | 배포 | **Dockerfile + docker-compose** (단일 컨테이너). k8s/Helm 은 향후 |

## 3. 매칭 및 핀포인트 탐색 로직 (핵심)

해시는 검색 엔진의 질의어로 쓸 수 없으므로 **"결합 쿼리로 핀포인트 후보 수집 → 후보 추출 → 해시 대조"**의 3단계 파이프라인을 구축한다.

### 3.1. 1차 외부 검색 (노이즈 압축 쿼리 & 페이지네이션)
- **문제점 인식**: `sk_live`, `ghp_`, `AKIA` 등 흔한 prefix만으로 검색할 경우, 전 세계 오픈 소스에서 수십만 건의 노이즈가 발생하여 100건 상한 뒤로 내 키가 밀려 **치명적인 미탐(False Negative)**이 발생함.
- **해결책 (Prefix + Postfix 결합 쿼리)**:
  - 검색어: `f'"{spec.prefix}" "{spec.postfix}"'`
  - 7자 prefix와 7자 postfix가 동시에 한 파일에 존재할 확률은 전 세계 웹을 통틀어도 수~수십 건 이하로 수렴하므로, **수억 개 파일 중 실제 내 키가 포함된 파일이 검색 결과 1순위로 즉시 노출됨.**
- **페이지네이션 전수 조사**:
  - 검색 결과가 100건을 초과할 경우 1페이지에서 멈추지 않고 `page=1..10`(GitHub 최대 1,000건)까지 페이지를 순회하며 누락 없이 전수 수집.

### 3.2. 2차 내부 정규식 후보 추출
```
KeySpec(prefix, postfix, sha256, length?, charset?) 로 정규식 생성
패턴:  (?<![A-Za-z0-9_\-])\b{prefix}[{charset}]{a,b}{postfix}\b(?![A-Za-z0-9_\-])
- length 있으면: a = b = length - len(prefix) - len(postfix)
- length 없으면: a=1, b=256 (안전 상한), charset 기본 = [A-Za-z0-9_-]
- 앞뒤 경계 검사로 다른 영숫자에 포함된 서브스트링 오탐 원천 차단
```

### 3.3. 3차 SHA-256 해시 대조
```
각 후보에 sha256() 계산 후 알려진 sha256 과 비교:
- 일치        → confidence=confirmed,    severity=critical (확정 노출, 수학적 오탐률 0%)
- 패턴만 일치 → confidence=pattern_only, severity=low      (해시 불일치, 경고 수준 낮춤)
```

**판정(verdict)**

| verdict | 조건 |
|---------|------|
| `EXPOSED` | confirmed 발견 1건 이상 (실제 내 키 노출 확정) |
| `NOT_FOUND` | 후보 없음 / confirmed 없음 (안전) |
| `INCONCLUSIVE` | 소스 오류로 일부 단계 미완료 (pattern_only 만 있는 경우 포함) |

## 4. API 설계

### `POST /scans` — 스캔 시작

요청:
```json
{
  "key_spec": {
    "name": "my-service-prod-key",
    "prefix": "sk_live",
    "postfix": "a1b2c3d",
    "sha256": "<hex 64자>",
    "length": 48,
    "charset": "base62",
    "custom_charset": "A-Za-z0-9_-",
    "key_type": "custom"
  },
  "stages": ["github", "web"],
  "options": {
    "max_results_per_source": 100,
    "include_pattern_only": true,
    "fetch_timeout_s": 10,
    "deep_scan": true,
    "qualifiers": ["filename:.env", "filename:config"]
  }
}
```

- `deep_scan`: true 시 1페이지(100건)에서 멈추지 않고, 결과가 더 존재할 경우 최대 허용 한도(`max_results_per_source` 또는 API 상한 1,000건)까지 페이지네이션을 돌며 **전수 탐색**.
- `qualifiers`: (선택) GitHub 검색 한정자 목록. 특정 조직(`org:company`), 특정 파일명(`filename:.env`) 등을 지정하여 집중 추적 가능.

응답 `202 Accepted`:
```json
{ "job_id": "uuid", "status": "queued", "poll_url": "/scans/uuid" }
```

### 비동기 실행 방식
- `asyncio.create_task` 로 워커 실행, 잡 상태는 `job_store` 의 dict + `asyncio.Lock`.
- 동시 실행 잡 수 제한(`MAX_CONCURRENT_JOBS` 세마포어), 잡 내부 페이지 fetch 동시성 제한(`MAX_CONCURRENT_FETCHES`).

## 7. 보안·안전 및 실전 탐색 정확도 고려사항

- **미탐(False Negative) 방지 — 결합 쿼리 의무화**:
  - `prefix` 단독 검색은 전 세계 오픈 리포지토리의 수십만 건 노이즈로 인해 내 키가 검색 결과 상한(100건) 뒤로 밀려 **실제 노출된 키를 절대 찾지 못하는 치명적 결함**을 유발함.
  - 따라서 반드시 `"{prefix}" "{postfix}"` 결합 쿼리를 사용하여 전 세계 검색 결과를 수~수십 건 이내로 1차 압축한 후 정밀 매칭을 수행함.
- **페이지네이션 전수 스캔 (Deep Search)**:
  - 1페이지(100건)만 확인하고 멈추지 않고, 결과가 더 존재하는 경우 최대 1,000건까지 페이지를 넘겨가며 전수 수집.
- **GitHub 보조 레이트리밋(Secondary Rate Limit) 방어**:
  - 연속 페이지 조회 시 급격한 호출로 인한 403 차단을 방지하기 위해 요청 간 인터벌(예: 0.5초) 및 exponential backoff 적용.
- **키 마스킹 일관성**: 전체 키/후보 문자열을 응답·로그·예외 메시지에 절대 노출하지 않는다. `redaction.py` 를 단일 지점으로 두고 로깅 필터도 적용. 출력은 항상 `prefix…postfix`.
- **요청 본문 로깅 비활성**: `sha256` 자체는 민감정보가 아니지만 요청 본문 로깅은 끈다.
- **SSRF 가드**: 웹 검색 결과의 임의 URL 을 fetch 하므로 `localhost`·사설/링크로컬 IP·메타데이터 IP(169.254.169.254)·비 http(s) 스킴 차단, 리다이렉트 횟수·응답 크기 상한.
- **공급자 ToS 준수**: 공식 API 만 사용. 구글 결과 스크래핑 금지.
- **GitHub Code Search 한계 명시**: 공개 + 기본 브랜치 + 인덱싱된 리포만 지원, 비공개 리포 및 삭제된 커밋 히스토리는 별도 점검 필요.

## 8. 테스트 & 린트 계획

- **린트/포맷**: `ruff` (lint + format). `pyproject.toml` 에 설정.
- **테스트**: `pytest` + `pytest-asyncio` + `respx`(httpx 목킹) + `httpx`/`TestClient`.
- 커버리지 대상:
  - `matcher`: 정규식 빌드, 해시 일치/불일치, 엣지케이스(length 미지정, charset custom, prefix·postfix 인접, 유니코드/개행 포함 텍스트)
  - `redaction`: 다양한 입력 마스킹, 로깅 필터
  - `key_spec`: 검증 실패 케이스(잘못된 sha256 길이, 빈 prefix 등)
  - `github_code`: **결합 쿼리 생성 검증, 다중 페이지(pagination) 전수 순회 검증, 403/레이트리밋 핸들링**
  - `fetcher`: SSRF 가드 차단 케이스 (사설망, 루프백, 메타데이터 IP)
  - `engine`: 가짜 소스 주입해 오케스트레이션·verdict 산출
  - API: `202` 응답, 폴링 상태 전이, 존재하지 않는 job_id `404`, 인증 실패 `401`

## 9. 개정 반영 구현 로드맵

| 단계 | 작업 내용 | 상세 목표 |
|---|---|---|
| **A** | `github_code.py` 쿼리 전략 개선 | `f'"{spec.prefix}" "{spec.postfix}"'` 결합 쿼리 적용 (노이즈 99.99% 압축) |
| **B** | GitHub API 페이지네이션 전수 스캔 구현 | `page=1..N` 다중 페이지 순회 및 최대 1,000건 전수 수집 로직 추가 |
| **C** | API 옵션 및 모델 확장 | `ScanOptions`에 `deep_scan`, `max_pages` 파라미터 지원 |
| **D** | 실전 모의 테스트 작성 | 대량의 검색 결과 페이지네이션 및 결합 쿼리 동작을 검증하는 목킹 테스트 추가 |

## 10. 기록해 둔 가정

- prefix/postfix ≈ 7자, 하나의 연속된 토큰이며 postfix 는 키의 실제 끝부분.
- length·charset 미지정 시: 중간부 길이 [1,256], charset `[A-Za-z0-9_-]` 로 가정.
- confirmed 해시 일치 1건이면 `EXPOSED` 로 판정.
- "삭제 권고" = 리포트 텍스트 + 삭제 요청 메시지 템플릿. v1 에서 자동 폐기·자동 메일 발송은 하지 않는다.
